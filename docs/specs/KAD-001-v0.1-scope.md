# KAD-001: v0.1 product scope and minimum CLI workflow

> **Status:** Accepted product boundary. This document specifies intended behavior; it does not mean the CLI is implemented.
> **Milestone:** v0.1. **Owner task:** KAD-001. **Recorded:** 2026-11-06.

## Goal and release policy

Ship an offline, project-local task manager implemented in Odin, operated through a native CLI on macOS, Linux, and Windows. A task is a Markdown document with YAML frontmatter. Developers and coding agents must be able to use the same files with a text editor or CLI, without a database, daemon, hosted service, or MCP server.

v0.1 must contain the complete safe core below. Usability improvements explicitly listed for v0.1.x are **deferred, not dropped**: each remains an unchecked roadmap task with acceptance criteria, planned after v0.1 and before boards in v0.2. File safety, integrity checks, and core CLI/JSON behavior are never deferrable to meet a release date.

**Testing policy:** [KAD-007 Section 7](KAD-007-fixture-corpus-v1.md#7-minimum-necessary-tests-agent-rules) governs implementation work and coding agents. Cover distinct accepted requirements and concrete regressions at the lowest effective level; there is no test-count or coverage-percentage target and no requirement to execute every fixture through every layer. Do not build a general test framework or a mandatory large-volume suite ahead of a demonstrated need.

## Project boundary and discovery

- **Hybrid operation:** `kadai init` explicitly creates project configuration, but it is optional. Core read and write commands work without initialization or a configuration file. Regular commands never create a configuration file implicitly.
- **Implicit project root:** use the current working directory (CWD) exactly, including when inside a Git repository. Do not walk to the Git root or search ancestors for configuration. Running from different subdirectories selects different projects unless `--project` explicitly fixes a root (KAD-003).
- **Explicit selection:** `--project <path>` selects exactly that existing directory for the command. `--tasks-root` can select another independent task collection within the selected project. Configuration lookup, physical paths and CLI precedence are fixed by [KAD-003](KAD-003-project-config-v1.md).
- **One project and one collection per command:** each effective task collection has its own task IDs, dependencies, history and lock, even when collection directories overlap. No cross-collection links, queries, or global index in v0.1.
- **Layout:** tasks live under one configurable root per collection, with arbitrary folder/subfolder organization. `tasks/` is the default and `tasks.root: .` is supported. Boards default to `boards/` within the effective task root; [KAD-003](KAD-003-project-config-v1.md) defines paths, exclusions and initialization.

## Documents and task identity

- **Authoritative storage:** Valid task `.md` files are authoritative for task state. Ordinary Markdown is ignored. Invalid task candidates are diagnosed separately and may allow diagnostic-only partial reads, never silent promotion to valid tasks (KAD-002/KAD-006).
- **No required body sections:** arbitrary or empty Markdown bodies are allowed. Custom properties belong under `custom`; unknown top-level keys are schema errors and retain their original text. A schema-invalid task only permits a supported directed repair of the invalid field, not unrelated mutations (KAD-006).
- **Stable identity:** task IDs remain unchanged across file moves and renames. Physical folder nesting is organizational only; one logical parent and independent prerequisite relationships use IDs. Exact ID format and semantics belong to KAD-004 and KAD-005.
- **Safe mutations:** unsafe patches fail without changing task data. Kadai writers coordinate the complete scan, validation and commit, including read sets and collection-membership checks across overlapping collections, not only files being written. They check source identity/hash immediately before atomic replacement and keep private immutable pre-write recovery copies. A non-cooperating external editor can save between final verification and replacement, so **absolute lost-update prevention cannot be guaranteed**. KAD-003/KAD-006/KAD-029/KAD-030 define the coordination, phase-specific failure effects and recovery boundary.
- **Filesystem safety:** supported writes preserve ownership, file mode, ACLs and extended attributes or fail closed. Refuse unsafe symlinks, hardlinks and unsupported security metadata (KAD-026/KAD-029).
- **ID history:** Markdown remains authoritative for task state; a small, durable, collection-local used-ID record under `<tasks.root>/.kadai/` stores allocation history only (not a DB). Generated IDs recorded by Kadai cannot be reused after task deletion while that history is retained, even without `kadai init` (KAD-004/KAD-037). Version control is entirely optional.

## Required v0.1 workflow

| User action | Minimum capability |
| --- | --- |
| Start using a project | Work with no config from CWD; optionally run `kadai init`; select a project with `--project` or a collection with `--tasks-root` |
| Create | `add` writes `status: todo` when no status was specified; creates tasks with empty body from title alone, or Markdown body from `--body-file <path>` / `--stdin` |
| Read | `list` and `show`; deterministic results; basic list filters by status, directory, tag, and parent, with a stable default order |
| Update | Set/unset supported metadata, change status, and use an external editor; handwritten changes are visible to the next read |
| Organize | Move/rename eligible files and directories within the effective collection without changing ID-based references; set/remove one logical parent |
| Relate | Add/remove prerequisites; inspect immediate dependencies and dependents; compute ready/blocked without storing redundant state |
| Inspect | `tree`, `ready`, and `validate`; validation detects duplicate IDs, missing/invalid links, self-links, and cycles without modifying files |
| Remove | Explicit, safe task removal with reference checks and no accidental overwrite |
| Automate | Human-readable terminal output and machine-readable JSON for queries/mutations, stable error/exit behavior, and noninteractive safe defaults |

Examples below convey the required user journey, **not frozen command grammar**. Exact subcommand/flag syntax and data shapes will be specified by KAD-047, KAD-050, and KAD-051.

```sh
# Work from the intended project CWD, or use --project; 'kadai init' is optional
kadai add "Implement parser"
kadai add "Review YAML edge cases" --body-file ./notes.md
cat ./task-body.md | kadai add "Write tests" --stdin
kadai list --json
kadai show T-001
kadai status T-001 in_progress
kadai edit T-001
kadai parent add T-003 T-001
kadai dep add T-003 T-002
kadai tree
kadai ready --json
kadai validate
# 'set', 'move', and 'remove' are also core commands; exact syntax is pending.
```

IDs above are placeholders, not a chosen ID format. `--body-file` and `--stdin` supply the **Markdown body**, not a second authoritative frontmatter header.

## Baseline acceptance for the v0.1 release

1. A project without a config supports the full read/write workflow. The CWD is the default project; `--project` selects an exact existing path. `--tasks-root` selects independent collections, with the documented caveats for overlapping roots.
2. Creating with only a title produces a valid task with an empty body. Creating with a body file or stdin preserves that Markdown content without adding prescribed sections.
3. Ordinary Markdown is ignored; valid nested tasks enter the index and invalid task candidates receive separate diagnostics. Hand-edited task content appears on the next read.
4. Supported metadata writes preserve unrelated bytes and supported file security metadata; Kadai-coordinated conflicting operations serialize or fail, even when they write different files but depend on the same graph or inventory. Non-cooperating external-editor races remain documented, with pre-write recovery copies.
5. ID-based references survive eligible moves; parent and prerequisite links are independent. Duplicate IDs (including Git merges) quarantine all matching tasks from ID-based operations until explicit repair. Recorded CLI-generated IDs are not reused after deletion.
6. Queries and mutations expose deterministic human and JSON output. JSON output contains no logs; failures use documented exit codes and stderr. Predictable output-serialization errors are checked before persistence. An output failure after commit is not a no-effect rejection and must not trigger an automatic retry or rollback (KAD-006).
7. A representative CLI-to-file workflow passes on macOS, Linux and Windows, with targeted native checks for link/metadata safety, conflicting writers and recovery. Reuse domain/parser tests instead of duplicating the whole fixture corpus at the CLI layer. Recovery must not overwrite a later edit.
8. Title-only creation writes `status: todo`; a hand-written task without `status` is invalid rather than defaulted.

These are release acceptance requirements, **not evidence that code or tests already exist**. KAD-007 supplies the Phase 0 fixture corpus and minimal-testing policy; Phase 6 validates release behavior.

## Explicitly deferred and excluded

| Target | Scope | Roadmap work |
| --- | --- | --- |
| v0.1.x | Advanced/multi-criteria filtering beyond the basic v0.1 filters | KAD-080 |
| v0.1.x | User-defined sorting and additional ordering modes beyond stable default ordering | KAD-081 |
| v0.1.x | Rich dependency graph output beyond immediate prerequisites/dependents and readiness | KAD-082 |
| v0.1.x | Additional CLI conveniences beyond safe core commands and JSON automation | KAD-083 |
| v0.1.x | Explicit `kadai import` for existing ordinary Markdown, preserving source and preventing overwrites | KAD-084 |
| v0.2 | Optional, manually curated Markdown Kanban boards | Phase 7 |
| v0.3 | Full-text search, editable custom metadata, progress notes, and advanced agent ergonomics | Phase 8 |
| Outside current roadmap | TUI and desktop UI | No implementation task scheduled |

Cross-project operations, globally unique IDs, and a hosted/cloud service are also outside v0.1. An import command is **not** part of v0.1 and must never run automatically.
